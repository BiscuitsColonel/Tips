# AWS 環境の保守と障害一次対応を外部へ委託するときに先に決めておくこと

AWS 上のシステムの保守作業とアラートの一次対応を運用委託先に任せる際、「何を頼めて何は頼めないか」を決めるために整理したメモ。契約や手順書に落とす前に、作業ごとに線を引いておく。

（2021-09 時点のメモ。業務システムの運用設計で検討した内容から、一般化して書いた。料金は当時の値）

## 定常作業は「頼めるか」ではなく「頼んだ結果どうなるか」で分ける

| 作業 | 線引きの考え方 |
| --- | --- |
| セキュリティグループなどの設定変更 | 依頼元で実施するか委託するかを決める。変更の根拠（接続先が変わった等）は依頼元が持つ |
| サーバーのスペック変更（EC2・Aurora） | サービス停止を伴うので、事前に承認フローを決める。深夜・休日にしかできない作業なら代行する価値が大きい |
| コンテナのスケールアウト・イン（ECS） | 起動数を変えるだけで無停止。ALB・NLB は自動スケールするが、急激な増加が見込まれるときは AWS へ事前に申請しておく |
| バックアップのリストア | 自動バックアップからのインスタンス単位の復元までは代行できる。データの中身に触る作業は代行できない |
| 証明書の更新 | 手元で発行した証明書のインポートは代行できるが、発行そのものは頼めない。ACM で発行しておけば更新自体が自動になり、作業が減る |
| アプリのデプロイ | デプロイが Git への push を契機に走る作りなら、代行には委託先への Git のアカウント発行と権限の絞り込みが要る。手順を自動化しておき、その実行だけを頼む形が安全 |
| WAF のルール変更 | 頼むなら細かい指示と手順が要る。「よしなに」は通用しない |
| AWS サポートへの問い合わせ・上限緩和 | 契約者である依頼元が窓口になる |

踏み台（SSM セッション）に委託先を入れるかどうかで、OS 上の作業が委託範囲に入るかが決まる。アクセス制御が厳しい環境では、入れないほうに寄せる。入れないなら OS 上の作業は範囲外になる。

## 障害の一次対応を頼むための前提

一次対応を成立させる条件は4つ。

- アラートが委託先へ通知される
- 件名だけで何のアラートか分かる
- 通知先がメールだけ（チャットや電話に頼らない）
- 対応手順がアラートごとに書かれている

想定パターンごとに、「手順どおりに実施」か「呼び出し」かを分けておく。

- URL の外形監視がダウンを検知: 再起動に相当する操作（ECS なら強制デプロイ）を1回やり、それでも直らなければ呼び出し
- コンテナやプロセスのダウン: 同様に手順で再起動し、直らなければ呼び出し
- リソース使用率の高騰（例: Aurora の CPU 張り付き）: スペックアップは判断が要るので呼び出し。手順があれば「先にスペックアップして事後連絡」も可能にできる
- クラウド事業者側の大規模障害: 委託先に期待しない。依頼元側の連絡手段を別に用意する

## 外形監視は CloudWatch Synthetics だと意外に高い

URL の外形監視を CloudWatch Synthetics の Canary で組むと、1回の実行が約 0.0019 USD。1分おきに30日走らせると 43,200 回で約 82 USD / URL になる（当時の料金。最新は[公式の料金ページ](https://aws.amazon.com/cloudwatch/pricing/)で確かめる）。委託先が外形監視のオプションを持っている場合は、そちらのほうが安いことがあるので、見積もりを比べる。
