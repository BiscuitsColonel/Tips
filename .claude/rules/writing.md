# Tip の書き方

## 残す基準

AI に聞けばすぐ出てくる内容は残さない。残すのは、AI が出力しにくい内容だけにする。

残すもの:

- 自分で検証・計測した結果（設定を変えたときの挙動、性能の比較）
- 実際に踏んだ障害・エラーと、その原因と解決（特定のバージョン・環境の組み合わせで起きたもの）
- 公式ドキュメントに書かれていない、または見つけにくい挙動
- 判断の記録（なぜその構成・設定にしたか、何と比べて何を捨てたか）
- 実際の運用で使った手順の勘所（順序に依存する点、落とし穴）
- 自分の言葉で整理したまとめ（複数の考え方の比較、使い分けの基準、自分の方針まで書いたもの）。個々の用語の説明が一般知識でも、どう整理し、どこで線を引いたかに価値がある

残さないもの:

- コマンドやオプションの一覧、インストール手順、公式チュートリアルの写し
- 一般的な概念の説明、書籍・記事の要約

1つのメモに両方が混ざっているときは、残すものの部分だけを短く書く。一般的な前提は1〜2文に縮めるか、公式ドキュメントへのリンクに置き換える。

### 判断の例

境界で迷ったときは、実際にこう判断した例に合わせる。

| メモ | 判断 | 理由 |
| --- | --- | --- |
| `terraform plan` を `-parallelism=30` にして 69 秒が 31 秒になった | 残す | 自分の環境での実測値 |
| psql のよく使うオプション一覧 | 落とす | マニュアルの抜粋 |
| HAProxy を Pacemaker で冗長化し、障害の種類ごとに切り替え時間を測った | 残す | 自分で測った試験結果と、設定値を選んだ理由 |
| Pacemaker・Pgpool のインストール手順 | 落とす | 手順そのものは公式にある。ハマった点だけを別に残す |
| サポートへの問い合わせで、回答から初めて分かった挙動 | 残す | マニュアルに書かれていない |
| 同じ問い合わせ記録のうち、回答がマニュアルの説明だったもの | 落とす | 調べれば分かる |
| デザインパターン・要件定義とは何か | 落とす | 一般論の要約 |
| DDD とクリーンアーキテクチャを1つの題材で通して整理し、MVCS との使い分けと AI 時代の方針まで書いたもの | 残す | 比較と線引き、方針が自分の整理 |
| 運用設計で決めたアラートのしきい値と、そう決めた理由 | 残す | 判断の記録（固有の値は伏せる） |
| 他人のスライド・PDF・Web 記事の要約 | 落とす | 原本を読めば足りる |
| EOL 後の CentOS で yum が動かないときに実際にやった対処 | 残す | 特定の環境で踏んだ障害と解決 |
| 自分で書いたシェルの小技（awk・sed の一行） | 落とす | AI に聞けば同じものが出る |

外部のメモをまとめて取り込む手順は `.claude/skills/import-tips/SKILL.md` にある。

## 1ファイルの形

- 1行目は `# タイトル`。README の一覧はこの行から作られるので、何の Tip かが分かる文にする（「設定」「使用方法」だけにしない）
- タイトルの直後に、何に使う Tip かを1〜2文で書く
- コードやコマンドだけのファイルを置かない。`.sh`・`.sql` 単体ではなく、md のコードブロックに入れて説明を添える
- コードブロックには言語名を付ける（`sh`・`sql`・`python` 等）
- Web の記事を転記するときは、冒頭に出典を書く。HTML のまま貼らず Markdown にする
- 同じトピックの小さいメモは、ファイルを増やさず既存の md に節として足す

## 情報の鮮度

- バージョン・廃止予定・UI の場所のように変わる情報は、公式ドキュメントで確かめてから書き、「（YYYY-MM 時点）」と添える
- 古い手順を残すときは、新しい手順を先に書き、古いほうに「〜以前の場合」と条件を付ける

## 載せない情報

このリポジトリは public で公開している。勤務先の社内情報と認証情報を入れない。

push した時点で公開される。あとからファイルを消しても、git の履歴と PR の差分（Files changed の削除行）に残り、誰でも読める。履歴は書き換えられるが、GitHub が PR のために保持している参照（`refs/pull/*`）は force push では消えず、リポジトリを作り直すか GitHub Support に依頼するしかない。それでも、公開中に作られたクローン・フォークに残った分は消せない。

漏れたときの順番:

1. 認証情報なら、まず失効させて再発行する。履歴から消すより先にやる（消しても、取得された値は使える）
2. ファイルを直し、履歴を書き換える（このリポジトリでは、全履歴を1コミットにまとめた）
3. PR の差分に残っていれば、リポジトリを作り直す

漏れを確実に止められるのはコミットの前だけなので、`check-tips.py --staged` を pre-commit hook（`.githooks/pre-commit`）で毎回走らせ、通らないコミットは止める。`--no-verify` で hook を飛ばさない。既知の形式のトークンは GitHub の push protection（このリポジトリで有効、2026-11 時点）も push の時点で止めるが、社名・アカウント ID・パスワードは止めないので、hook が主の防御になる。

- 実在の AWS アカウント ID・バケット名・ロール名・社員のメールアドレス・社内リポジトリ名
- アクセスキー・トークン・パスワード（失効済みのものも）
- これらが写ったスクリーンショット
- 設定ファイルのメタデータに残った名前。IDE のプロファイル名、エクスポートした設定の作成者、生成元のプロジェクト名など。本文を書き換えても見落としやすい（Eclipse のフォーマッタ設定のプロファイル名に、業務のプロジェクト名が残っていた例がある）

例にはダミー値を使う。AWS アカウント ID は `123456789012`、バケットは `example-bucket`、ドメインは `example.com`。

勤務先・顧客の業務で得た知見は、コードや文書をコピーしない。そこで得た技法・考え方だけを、自分の言葉で汎用の Tip として書き起こす（社名・顧客名・パッケージ名・固有の構成は残らない形にする）。

## 自作のコード

自作プロジェクトのコード一式はリポジトリに置かない。プロジェクトごとに「何をするものか・使い方・肝の設定や工夫」を md にまとめ、代表的なコード片だけを載せる。

## 追加・リネームしたら

```sh
$ python scripts/gen-readme.py
$ python scripts/check-tips.py
```

README を作り直して Tip と同じコミットに含め、検査が通ることを確かめる。

勤務先・顧客の名前は、リポジトリに書くとそれ自体が漏れになる。検査させたい語は、git の管理外の `.claude/sensitive-words.local.txt`（1行1語）に置く。`check-tips.py` はこのファイルがあれば読み、大文字小文字を区別せずに探す。

## 検証方法

| 確認項目 | 手段 | 強制レベル |
| --- | --- | --- |
| 1行目が `# タイトル` | `scripts/check-tips.py --staged` を `.githooks/pre-commit` で実行 | block（`core.hooksPath` を設定した clone のみ。`--no-verify`・GitHub 上での直接編集は通る） |
| 相対リンクが切れていない | 同上 | block（同上） |
| README が実ファイルと一致 | 同上（ステージした README を生成結果と比較） | block（同上） |
| 認証情報・実在の ID が無い | 同上（AWS のキー・Slack トークン・秘密鍵・12桁の数字・平文パスワード。Tip に限らず、`scripts/tests/` を除く全テキストファイル）。既知の形式のトークンは GitHub の push protection も止める | block（同上） |
| 勤務先・顧客の名前が無い | 同上と `.claude/sensitive-words.local.txt` | block（同上） |
| 社名・プロジェクト名の書き方が違うもの、リストに無い名前 | 目視。コミット前に差分の固有名詞を見る | recommend |
| AI で出せる一般論だけになっていない | 目視（上の「判断の例」） | recommend |
| 時点依存の情報に日付がある | 目視 | recommend |
