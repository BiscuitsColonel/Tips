# バッチで KMS のデータキーを使い、AES-CTR で項目を暗号化する

S3 のファイルを読み、行ごとに一部の項目を暗号化して出力する Spring Batch を作ったときの、暗号化まわりの設計メモ。鍵の持ち方と、CTR モードで踏みやすい点を書く。

（2022-02 時点のメモ。コードは載せない）

## 鍵の持ち方

- アプリが持つのは「KMS で暗号化したデータキー」だけにする。DB のテーブルに暗号化済みデータキーを世代ごとに入れておき、バッチの起動時に最新の1行を取って KMS の `Decrypt` で復号し、メモリ上だけで使う
- 復号は起動時に1回だけにする。行ごとに KMS を呼ぶと、呼び出し回数と遅延が行数に比例して増える
- 初期化ベクトル（IV）は秘密ではないので、環境変数で隠す必要は無い。大事なのは再利用しないこと（後述）。当時は IV を環境変数で渡す設計で、環境変数は1つの値なので、そのままでは全項目が同じ IV になる
- ローカルの動作確認では、S3 と KMS の代わりに minio と local-kms にクライアントを向ける。設定クラスで接続先を切り替えられるようにし、テスト用のキーはテスト設定の中だけに置く

## AES/CTR/NoPadding を選ぶ理由と、踏みやすい点

CTR はパディングが要らず、暗号文の長さが平文と同じになる。固定長の項目を扱うときに扱いやすい（文字列で保存するために Base64 にすると、長さは約 4/3 倍になる）。

一方で、当時の設計の問題点として、次を整理し直す。

- IV を環境変数で渡すと、起動ごとに1つの値に固定され、全項目が同じデータキー・同じ IV になる。CTR は同じ鍵・同じカウンターブロックから同じ鍵ストリームを作るので、2つの暗号文の XOR が平文どうしの XOR になり、片方の平文が分かれば他方も分かる。[MDN: AesCtrParams](https://developer.mozilla.org/en-US/docs/Web/API/AesCtrParams) は、同じ鍵でカウンターブロックの値を2回使ってはならないと書いている
- `Cipher` を1つ作って複数の項目に `doFinal` を続けて呼ぶ実装でも同じことが起きる。`doFinal` のたびに `init` 直後の状態に戻るため（[Cipher の Javadoc](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/crypto/Cipher.html) に「`init` で初期化された時点の状態に戻る」とある）、項目ごとに同じ鍵ストリームが使われる
- 直し方は、項目ごと・レコードごとに IV を変えること。IV は秘密ではないので、暗号文の先頭などに付けて持ち回ってよい（JCA の[リファレンスガイド](https://docs.oracle.com/en/java/javase/17/security/java-cryptography-architecture-jca-reference-guide.html)も IV は「ランダムであるべきだが秘密にする必要はない」としている）。ただし IV を持ち回ると、固定長のまま保存できるという CTR の利点は薄れる
- GCM に替えても解決にはならない。GCM もノンスの再利用は致命的で、同じ鍵とノンスの組を再び使ってはならない（JCA リファレンスガイド: "callers should not re-use key and IV combinations for encryption"）。しかも認証タグが付くので、暗号文は平文よりタグ長（通常 128 ビット = 16 バイト）だけ長くなる。固定長にこだわるなら CTR + 項目ごとの IV、改ざん検知も要るなら GCM + 項目ごとのノンスで、どちらも IV の管理が要る
- 鍵を替えるときは、データキーのテーブルに新しい行を足す運用にしておくと、最新の行を取る実装のまま世代交代できる
- ファイル全体を暗号化するときは `CipherInputStream` で包んで読みながら書けば、全体をメモリに載せずに済む
