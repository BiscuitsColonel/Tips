# join_collapse_limit は結合全体ではなく、結合ツリーの塊ごとに効く

9〜11 テーブルを結合するクエリで、結合順がどこまでプランナに並べ替えられるかを `join_collapse_limit` / `from_collapse_limit` / `geqo_threshold` の関係から整理したメモ。設定値の意味そのものは[公式ドキュメント](https://www.postgresql.org/docs/current/runtime-config-query.html)を見る。`Leading` ヒントが効かない場面との関係は [pg_hint_planで結合順を指定できないときの対処](pg_hint_planで結合順を指定できないときの対処.md) を参照。

（2021-04 時点のメモ。PostgreSQL のバージョンは元メモに記載なし。値はデフォルトで、元メモの記載による）

## 前提

`join_collapse_limit` と `from_collapse_limit` のデフォルトは 8、`geqo_threshold` のデフォルトは 12。9〜11 テーブルを結合するとき、プラン作成がどう進むのかが疑問だった。

## 整理した結果

結合の処理は、結合のツリー構造を再帰的にたどって行われる。ツリー上のある地点から下の構造を調べ、その中のテーブル数が collapse_limit 以下なら、その範囲の中で並べ替えを含めてプランニングする。

- 結合テーブルが 8 までは、明示的な JOIN の並べ替えが起きる
- 9〜11 番目の表は SQL に書いた順のまま扱われるかどうかが、ツリーの形に依存する。「9〜11 番目は SQL の順」と決まっているわけではない
- 例として、4 テーブル (A,B,C,D) の塊と別の 5 テーブル (E,F,G,H,I) の塊があるとする。合わせると 9 で上限を超えるので、(A,B,C,D) と (E,F,G,H,I) を混ぜた並べ替えはされず、それぞれの塊の中だけで組み合わせを探す
- 後段の塊が 4 テーブル (E,F,G,H) なら、合計 8 で上限以内なので、(A,B,C,D,E,F,G,H) 全体を組み合わせたプランニングになる

つまり、テーブル数の合計だけでは結合順の自由度は決まらず、どの JOIN をどの括りで書いたかで変わる。上限を超えて意図しない結合順になっているときは、SQL の書き方（サブクエリや JOIN の括り）を見直すか、`SET join_collapse_limit` を引き上げて試す。
