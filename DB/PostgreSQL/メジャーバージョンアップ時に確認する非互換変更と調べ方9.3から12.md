# PostgreSQL 9.2 から 12 へ上げるときに、既存の SQL・スクリプト・設定が壊れる変更と調べ方

メジャーバージョンアップの影響調査で、リリースノートの「非互換」項目を、自分の環境で確認するコマンドとセットにしたチェックリスト。全項目の翻訳ではなく、見落とすと実害が出やすいものだけを選んでいる。正本は各バージョンのリリースノート（<https://www.postgresql.org/docs/release/>）。

（2020-10 時点のメモ。9.3 から 12 までの非互換変更をまとめたもの）

調べ方の共通の型は、SQL ファイル群・シェルスクリプトを `grep` する（`SQLFILE` はアプリが発行する SQL を保存したもの）、`pg_dumpall -s` の出力を `grep` する、`postgresql.conf` の設定を `grep` する、の 3 つ。

## 設定ファイル・運用スクリプトに効くもの

| 上がる先 | 変更 | 調べ方 |
| --- | --- | --- |
| 9.3 | `replication_timeout` は `wal_sender_timeout` に改名 | `postgresql.conf` を grep |
| 9.3 | メモリ内ソートが割り当てた `work_mem` 全体を使えるようになった。設定値を見直す | `work_mem` を確認 |
| 9.3 | WAL ファイル名の末尾に `FF` も使われる。末尾 `FE` の次を `FF` とみなしていないか | WAL を扱うスクリプトを確認 |
| 9.5 | `checkpoint_segments` は `min_wal_size` / `max_wal_size` に置換。`max_wal_size = (3 * checkpoint_segments) * 16MB` を目安にする | `postgresql.conf` を grep |
| 9.5 | `pg_ctl stop` のデフォルトが `smart` から `fast` に。セッション終了を待ちたいなら `-m smart` | スクリプトを grep |
| 9.6 | `pg_stat_activity.waiting` が消え、`wait_event_type` / `wait_event` に | SQL を grep |
| 10 | `pg_xlog` → `pg_wal`、`pg_clog` → `pg_xact`、関数名の `xlog` → `wal`、`location` → `lsn`、`log_directory` のデフォルトが `pg_log` → `log` | スクリプトと SQL を grep |
| 10 | `pg_ctl` が起動・停止の完了を待つのがデフォルトに | スクリプトの前提を確認 |
| 10 | `pg_basebackup` がデフォルトで WAL をストリーム | オプションを確認 |
| 10 | Hash インデックスは `pg_upgrade` 後に再作成が必要 | `\di` などで種別を確認 |
| 10 | `shared_preload_libraries` などのクォートなしの値を小文字化しなくなった。大文字小文字を正しく書く | `postgresql.conf` を grep |
| 10 | `min_parallel_relation_size` は `min_parallel_table_scan_size` / `min_parallel_index_scan_size` に分離 | `postgresql.conf` を grep |
| 11 | `pg_dump --create` / `pg_restore --create` で DB 属性もダンプされる。`pg_dumpall -g` はロールとテーブルスペースのみ | バックアップスクリプトを確認 |
| 11 | 制約名の一意性が完全に強制される。重複する制約名があると問題になる | `pg_dumpall -s \| grep CHECK` |
| 12 | `recovery.conf` が廃止され `postgresql.conf` へ。PITR の既定が最新タイムラインまで進むように | レプリケーション・PITR の構成を確認 |
| 12 | `pg_verify_checksums` は `pg_checksums` に改名。`pg_restore` で標準出力へ出すには `-f -` が必要 | スクリプトを grep |
| 12 | 新しい B-tree の最大エントリ長が 8 バイト減ったため、`pg_upgrade` で上げたクラスタでは `REINDEX` が失敗することがある。`DROP INDEX` + `CREATE INDEX` で対処 | 運用手順を確認 |
| 12 | `DROP FUNCTION IF EXISTS` を引数なしで書くと、同名の関数が複数あるときエラーになる | SQL を grep |

## アプリケーションの SQL に効くもの

| 上がる先 | 変更 | 調べ方 |
| --- | --- | --- |
| 9.3 | `search_path` が変わるとキャッシュ済みプランを再作成する。プリペアドステートメントとスキーマ切り替えを併用していないか | アプリを確認 |
| 9.4 | JSON 変換で日付・時刻が ISO 8601 になる。`json` への変換前に `text` へ明示キャストする | SQL を grep |
| 9.4 | `EXPLAIN ANALYZE` の `Total runtime` が `Execution time` に | ログ解析を確認 |
| 9.4 | `DISCARD` がシーケンス状態も破棄する | SQL を grep |
| 9.5 | 演算子の優先順位が標準 SQL に合うよう変更（`IS NULL` と比較演算子の併用）。`operator_precedence_warning` を有効にして検証する | SQL を grep |
| 9.5 | PL/pgSQL 代入の型変換が代入キャストになる（boolean から文字列など） | 変換箇所を確認 |
| 9.5 | `pg_stat_replication.sent` が無効のとき 0 でなく NULL に | SQL を grep |
| 10 | SELECT リストの集合返却関数の実装が変わり、行数の違う結果の扱いが変わった | クエリ結果を実行して比較 |
| 10 | シーケンスのメタデータが `pg_sequence` に移動 | シーケンス情報を SELECT しているか確認 |
| 10 | 文単位トリガが文ごとに複数回起動されなくなった | トリガ定義を確認 |
| 11 | `pg_class.relhaspkey`、`pg_proc.proisagg` / `proiswindow` が削除（`prokind` へ） | SQL を grep |
| 11 | 拡張問い合わせプロトコルで `statement_timeout` が Execute メッセージごとに別々に適用される | `PREPARE` を使うアプリを確認 |
| 11 | 関数と列参照の曖昧さを解消するとき、構文形式を優先する（列名と同名の関数がある場合） | `pg_get_functiondef` で関数定義を grep |
| 12 | テーブルの `oid` 列の特別な扱いが廃止 | `oid` を使う SQL を grep |
| 12 | `pg_constraint.consrc` / `pg_attrdef.adsrc` が廃止。`conbin` / `adbin` を使う | SQL を grep |
| 12 | `abstime` / `reltime` / `tinterval` 型が廃止 | `pg_dumpall -s` を grep |
| 12 | `information_schema` のオブジェクト名の列が `varchar` でなく `name` に | SQL を grep |
| 12 | `random()` / `setseed()` の動作がプラットフォームによらず統一 | 再現性を使う箇所を確認 |

## grep で判定できない項目

9.4 の「JSON 文字列のユニコードエスケープ」や 10 の「SELECT リスト内の集合返却関数」のように、grep では判定できず、実際にクエリを流して結果を比べるしかない項目がある。
