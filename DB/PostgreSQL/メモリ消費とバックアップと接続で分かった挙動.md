# メモリ消費・バックアップ・クライアント接続まわりで分かった挙動（サポート問い合わせより）

work_mem を超えるメモリ消費、PL/pgSQL のキャッシュ起因のエラー、pg_stop_backup の待ち、Windows のダンプ文字化け、psql のログイン失敗ログの本数など、他のメモに収まらなかったものをまとめたメモ。

（2020〜2021 年ごろのサポート問い合わせの記録。PostgreSQL 10〜12、Aurora PostgreSQL 11 の記録を含む）

## `work_mem` や `temp_buffers` を超えてメモリが減る

- 現象: 一時テーブルへの INSERT を実行するたびに、物理メモリとスワップがなくなって DB が落ちた。`work_mem = 32MB`、`temp_buffers = 16MB`、物理メモリ 32GB。
- 分かったこと:
  - `temp_buffers` はセッション単位の上限、`work_mem` は 1 つの SQL の中のソートやハッシュ 1 処理ごとの上限。ソートとハッシュが 10 個あれば最大 `work_mem × 10`。
  - データ量が増えても、実行計画が変わらずソートやハッシュの数が増えないなら、メモリ消費は増えない（`work_mem` を超える分はディスクに溢れる）。実行計画が変わって処理が増えたことが疑わしい。
  - `work_mem` と `shared_buffers` 以外にも、メモリを大量に使うものがある。パラメータの無いメモリ消費の代表例は次のとおり。
    - 解析段階で、プログラムが生成した `col1 = 1 OR col1 = 2 OR ...` が数 KB 続く SQL
    - 再帰 CTE（`WITH RECURSIVE`）や、再帰する関数（`max_stack_depth` 超過のエラーになりやすい）
    - 巨大な文字列をクライアントから受けて文字エンコーディング変換するとき（10MB の変換に 40MB を確保）
- 調べ方: DB が落ちるので実行しない `EXPLAIN INSERT ...` で計画を取り、ソートとハッシュの数を見る。

## PL/pgSQL の型違いエラーが別セッションでだけ出る

- 現象: 同じ関数を、`varchar` のまま渡す場合と、一度復号して `text` で渡す場合の 2 通りで呼ぶ。同じセッションなら成功し、別セッションで続けて実行すると、後から実行した側が型違いでエラーになる。
- 分かったこと: PL/pgSQL は 2 回目以降にキャッシュした実行計画を再利用する。関数内の RECORD 変数のある列に入る型が `varchar` と `text` で揺れると、キャッシュ済みの計画の型と実際の値の型が食い違う。
- 対処: 代入するときに型をそろえる（`schema.col::TEXT`）。

## `pg_stop_backup` の待ちとアーカイブ先

ベースバックアップ中だけ WAL のアーカイブ先を外部ストレージからローカルディスクに切り替える運用の意味は、サポートからは断定されなかったが、考えられる狙いは次の 2 点。

- `pg_stop_backup()` は、バックアップ中に使った WAL がアーカイブされるまで待つ（9.6 以前は必ず待つ）。アーカイブ先が遅いと戻りが遅くなる。待たない指定にすると、アーカイブが遅れたまま障害が起きたとき、完了したはずのバックアップからリカバリできなくなりうる。
- ベースバックアップの転送で外部ストレージの帯域が埋まると、アーカイブが進まず、オンラインの WAL ディレクトリが溢れうる。

## ダンプ・リストアを止めたいとき

`pg_stat_activity` の `application_name` が、`pg_dump`、`pg_restore` になっているものが対象のプロセス。`psql -f` でのリストアは `psql` のままで他のセッションと区別が付かないことがあるので、`usename`、`client_addr`、`backend_start` で絞る。ダンプやリストアの進捗率を取る方法は無く、`query` 列か `-v` の出力から推測するしかない。

## Windows で `pg_dump -v` の日本語が化ける

データベースが UTF-8 だと、コマンドプロンプトや PowerShell（SJIS 表示）で日本語のテーブル名やメッセージが化ける。ログをファイルに出しても、テーブル名は化けたまま。`chcp 65001` を実行してから `pg_dump` を実行してログをファイルに出す。`pg_dump --encoding SJIS` でも化けは避けられるが、SJIS で表せない文字が 1 つでもあるとエラーでダンプできなくなる。

## psql のログイン失敗ログが 1 回で複数行出る

- 現象: 存在しないユーザーで接続に失敗すると、1 回の操作でサーバーログに 2 行、環境によっては 3 行のエラーが出る。
- 分かったこと: `-W` を付けないと、psql はサーバーがパスワードを要求するかを確かめる接続を先に試す。さらに `sslmode` が `prefer`（デフォルト）で、サーバー側が `ssl = on` だと、SSL で接続できるかを確かめる試行も加わる。存在しないユーザーなら、試行ごとにエラーが出るので、2〜3 行になる。サーバー側が `ssl = off` なら SSL の試行は無い。
- 1 行にするには、`-W` を付け、`sslmode` を `require`（SSL を使っている場合）か `disable` にする。

## 大量 INSERT で洗い替えしたテーブルは ANALYZE が要る

毎日 `TRUNCATE` → 大量 `INSERT` で作り直すテーブルは、TRUNCATE で統計情報が切り捨てられ、INSERT 後は実データと統計がずれる。そのためインデックスを付けても効かないことがある。INSERT の後に `ANALYZE` する。作り直しのたびにインデックスを再作成する必要は無い。

## `auto_explain` の設定が与える影響

- `auto_explain.log_min_duration` の値の大小で、SQL の性能への影響は変わらない。実行計画のログは SQL の完了時に出るので、出るタイミングも変わらず、閾値以上かどうかで出るか出ないかが決まるだけ。30 分かかった SQL は、閾値が 1 時間なら出ない。
- `auto_explain.log_timing` が重いと言われるシステムは、時刻の取得（`gettimeofday()` のシステムコール）のオーバーヘッドが大きい OS を指す。環境次第なので、本番で有効にする前に測る。

## 10.13 での挙動の変更

- イベントトリガー関数（引数無し、戻り値が `event_trigger`）を、通常の関数のように `SELECT f();` と呼ぶと、10.13 以降は `ERROR: trigger functions can only be called as triggers` になる。
- `anyrange` だけを渡して `anyarray` の出力を推論させる多相関数は、10.13 より前は `cache lookup failed for type 0` になることがあった。

## 統計カウンターのオーバーフロー

`pg_stat_database` の `tup_inserted` などの累積値が `bigint` の上限を超えたとき、型変換や演算では境界チェックで `out of range` エラーになる。累積処理ではチェックされない箇所があり、その場合は黙ってオーバーフローする。

## `psql` の `-h` を省略したときのソケット

`-h` を省略すると UNIX ドメインソケットのディレクトリを使う。ソース標準は `/tmp`（`pg_config_manual.h` の `DEFAULT_PGSOCKET_DIR`）で、変えるにはビルドが要る。環境変数 `PGHOST` があればそちらが優先。ディストリビューションが配るパッケージでは、9.4 以降は `/var/run/postgresql` がデフォルトになっているなど、パッチが当たっていて、ソースから入れたものと違う。
