# 主キーの重複・インデックス破損・truncate の Permission denied を切り分ける

主キー値が重複した行ができた、VACUUM がインデックスのエラーを出す、`could not truncate file ... Permission denied` が出る、といった「データ破損が疑われる」場面で、サポート問い合わせで分かった原因と対処をまとめたメモ。

（2020〜2021 年ごろのサポート問い合わせの記録。PostgreSQL 10〜12）

## VACUUM が出すインデックス破損のエラー

次の 2 つは、どちらもインデックスの破損を表している。

```text
ERROR:  left link changed unexpectedly in block N of index "..."
ERROR:  failed to re-find parent key in index "..." for deletion target page N
```

再構築の方法は 2 つ。

- `REINDEX`: 読み書きがロックされるので、実行中は実質停止。時間はデータ量次第なので、本番相当のデータ量の検証環境で計測してから決める。
- `CREATE INDEX CONCURRENTLY` と `DROP INDEX CONCURRENTLY` で置き換え: 読み書きは止まらないが、作成に時間がかかる。どちらも作業中は一時的に追加のディスク領域が要る。

## 主キーが重複した行ができる原因

原因は次の 4 つ。

1. インデックスの破損（主キーはインデックスで保証されるので、あるはずの値を見落とせば重複を許す）
2. テーブルデータ自体への不正な書き込み
3. 同じデータディレクトリで PostgreSQL が二重に起動した（異常終了後にプロセスが残ったまま再起動した場合。共有バッファが別々になるので重複検査をすり抜ける）。異常終了のあとは `postgres` プロセスが残っていないか確認して消すか、OS を再起動する
4. PostgreSQL のバグ。10.6 では該当するバグがあり、10.7 以降で直った

インデックスやテーブルが壊れる要因は、PostgreSQL のバグか、OS・ハードウェアの誤操作や障害。サポートの過去事例では、コネクションプールの利用が原因になったものは無い。

## 重複行の後始末

重複したままだと `pg_dump` の結果をリストアするときに主キー制約でエラーになるので、不要な側の行を消してから取る。

- 通常の `DELETE` が効かないときは、`SELECT ctid, * FROM t WHERE 主キー条件;` で `ctid` を確認し、`DELETE ... WHERE 主キー条件 AND ctid = '(ページ, 行)';` で消す。インデックスを使うと見つからないことがあるので、`SET enable_indexscan = off; SET enable_bitmapscan = off;` にしてから探す。
- それも駄目なら、対象テーブルだけ `pg_dump -t` で平文に出し、重複を手で消してリストアする。
- 終わったら `REINDEX`。
- どちらを残すか決めたいときは `SELECT xmin, * ...` で比べる。`xmin` は最後に更新したトランザクション ID なので、大きいほど新しいと推測できる。ただしトランザクション ID は周回する。更新量が極端に多くなければ周回は無視して `age(xmin)` が小さい方を新しいとみなしてよい、という回答だった。レコードの更新日時を知る標準機能は無い。
- インデックスが今どの行を指しているかは、インデックススキャンになることを `EXPLAIN` で確かめてから、インデックス列で絞った `SELECT ctid, * ...` で分かる。

## `could not truncate file ... Permission denied`

```text
ERROR:  could not truncate file "base/NNNNN/NNNNN" to N blocks: Permission denied
```

- 現象・条件: Windows で autovacuum の最中に出る。同じログで出ないテーブルがあるのは、テーブルの末尾が空いて切り詰め可能な配置になったかどうかによる。更新頻度が高いほど autovacuum の回数が増えるので、出る確率も上がる。
- 分かったこと: VACUUM は、末尾のブロックがすべて削除済みの行なら、ファイルを切り詰める（truncate）。このときの低レベルな I/O エラーに PostgreSQL は十分に対応できていない。「truncate は失敗したが、削除済みの行が再び見える」状態になりうる。1 回の発生で、そのブロック内の複数の行に影響する。回避すると PANIC でサービス全体を止める以外に良い実装が見つかっていないため、この実装になっている。
- 「Windows ＋ VACUUM の切り詰め ＋ Permission denied ＋ クラッシュリカバリ」の組み合わせでデータ破損が起きうる既知の問題。10.14、12.x、13.0 でも残っていた。
- 原因の典型は、ウイルス対策ソフトなどがバックグラウンドでデータディレクトリのファイルを開いてロックしていること。SQL の書き方やアプリの動きでは起きない（アプリがデータディレクトリのファイルを直接触っていれば別）。
- 対処: 10 では、データディレクトリをウイルス対策ソフトなどの対象から確実に外すのが最善。12 以降では VACUUM で切り詰めをしない指定ができる（[VACUUM の TRUNCATE オプション](https://www.postgresql.org/docs/12/sql-vacuum.html)。テーブル単位の `vacuum_truncate` も同ページに記載）。副作用は、一度肥大化したテーブルのファイルが、`FULL` なしの VACUUM や autovacuum では小さくならなくなること。切り詰めが働くのはたまたま末尾に空きが集まった場合に限られるので、影響は大きくない、というのがサポートの評価。
- 再現は難しい。autovacuum がファイルを読んだ後、結果を書き込むまでの間に、実行ユーザーが読み書きできないように権限を変える必要があるため。
