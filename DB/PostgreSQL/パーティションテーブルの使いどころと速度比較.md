# PostgreSQL のパーティションテーブルを使うべき場面と、実クエリでの速度比較

宣言的パーティション（PostgreSQL 10 以降）を入れるかどうかの判断材料。基本の作り方は公式ドキュメントを見る。ここには、判断の基準と、実際のクエリで試した結果だけを書く。

（2020-11 時点のメモ。検証した PostgreSQL のバージョンは元メモに無い。宣言的パーティションの制約は当時のもの）

## 使いどころの判断

- 向いているのは、特定条件で絞ったとき、検索する値が少数のパーティションの子テーブルにしか無い場合。さらに、一括の削除や追加が、パーティション単位の `DROP TABLE` や `ATTACH` / `DETACH PARTITION` で済む場合（`DELETE` より桁違いに速く、VACUUM のオーバーヘッドも出ない）。
- 向かないのは、問い合わせや更新がパーティションの大部分に触れる場合。pruning が効かず、子テーブルすべてのインデックスやランダムアクセスを使うことになり、かえって遅い。
- 滅多に使わないデータを、低コストで低速なストレージ（テーブルスペース）へ移す用途にも使える。
- パーティション数が増えるほど計画時間が増えるため、1 テーブルあたり 100 前後を目安にする。ハッシュは、範囲やリストで分けられないときにだけ使う。

## 注意点

- 親テーブルをまたぐ一意制約（グローバルインデックス）は無い。PRIMARY KEY や UNIQUE は子テーブルごとに作る必要があるので、メンテナンスするインデックス数が増える。
- 親への INSERT は子への振り分け処理が加わるので、理屈では直接の INSERT より遅くなる。実測では、通常テーブルへの 1 件 INSERT が平均 0.47 秒、パーティションテーブルへの 1 件 INSERT が平均 0.40 秒で、この環境では悪化しなかった（単位は元メモのまま。1 件 INSERT にしては 0.4 秒台は長く、秒かミリ秒かは未確認）。
- 子テーブルの数が変わる（ハッシュで余りの数が増える、など）ときは、対応する子テーブルを必ず作る。

## 実クエリでの比較

ある地域コードで絞って件数を集計する複数結合のクエリを、大きなテーブルを地域コードの値でリストパーティションにした場合と通常テーブルで比べた。パーティションキーの列を検索条件に含めて、その子テーブルだけが読まれる形で測っている。

| テーブル | 実行時間 |
| --- | --- |
| 通常テーブル | 約 3,046 ms |
| パーティションテーブル | 約 1,393 ms |

通常テーブルは別の複合インデックスで引いて残りをフィルタしていたのに対し、パーティションテーブルは対象の子テーブルだけをインデックススキャンして、約 2 倍速くなった。

パーティションキーの列は取りうる値が少なく（3 種類程度）、そのうち 1 つの値が全体の約半数を占めていた。その値で絞るクエリが最も多いという使われ方を前提に、リストパーティションを選んでいる。キーの偏りと検索の頻度を見て決める。
