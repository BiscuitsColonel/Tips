# PostgreSQL のサポート問い合わせで分かった、マニュアルを読んだだけでは気づきにくい挙動

運用中に出たログや現象について、PostgreSQL のサポート窓口に問い合わせて得た回答のうち、マニュアルを一読しただけでは分かりにくいものをまとめたメモ。

（2021-07〜2021-09 時点のメモ。PostgreSQL 10〜12 の環境での問い合わせ。関数名は当時のもので、PostgreSQL 10 以降は `pg_xlog` が `pg_wal` に、`pg_xlogdump` が `pg_waldump` に変わっている）

## スタンバイの参照クエリがキャンセルされる（コンフリクト）

ホットスタンバイで `terminating connection due to conflict with recovery` が出る原因は、更新対象のテーブルを直接参照していたときだけではない。

- 参照中のスナップショットが古いままだと、プライマリで自動 VACUUM が行を回収した WAL の適用が待たされる。待たされている間は、別テーブルの WAL もその後ろに並ぶ。
- `pg_stat_activity` のような統計情報ビューを SELECT しただけでもコンフリクトは起きる。統計情報そのものは WAL に載らず、プライマリとスタンバイで別々に持つので直接ぶつかることは無い。ただし、潜在的に古いデータを見うるトランザクションが動いていれば、その古いデータを壊す WAL の適用が待たされる。
- 統計ビューを引くときはシステムカタログも読み、カタログは共有バッファに載る。そのため `DETAIL: User was holding shared buffer pin for too long.`（共有バッファの PIN が解放されず WAL を適用できない）が出ることがある。PIN の仕組みはソースの `src/backend/storage/buffer/README` に書かれており、スタンバイ上のあらゆる SELECT で起こりうる。

対処の設定は `max_standby_streaming_delay`、`hot_standby_feedback`（プライマリ側で行の回収が遅れて肥大する代償がある）、`vacuum_defer_cleanup_age`。

## CREATE INDEX CONCURRENTLY がいつまでも終わらない

同時実行のインデックス作成は、インデックスを使いうる実行中のトランザクションがすべて終わるまで待つ。さらに 2 回目のスキャンの後は、そのスキャン前のスナップショットを持つトランザクションの終了も待つ。長いトランザクションや放置されたセッションが 1 つ残っているだけで終わらない。待ちには仮想トランザクションロックが使われる（ホットスタンバイの競合検出でも使われる仕組み）。終わらないときは `pg_stat_activity` で古い `xact_start` のセッションを探す。

## PANIC: could not write to file "pg_xlog/..." と Operation not permitted

WAL の書き出し失敗は PANIC になり、サーバー全体が停止または再起動する。同じログに `Operation not permitted` のファイルオープン失敗が散発していたら、WAL 以外の重要度の低いファイルでも OS レベルで失敗している。原因の候補は 3 つ。

- ファイルオープン数の上限に達した: `max_files_per_process`を下げるか（[公式ドキュメント](https://www.postgresql.org/docs/current/runtime-config-resource.html)）、OS 側の上限を上げる
- 権限違反: データディレクトリ配下が実行ユーザーの所有かを見る。SELinux の制限も疑う
- 強制排他制御に当たった: ファイルシステムを強制排他制御にした場合に限られ、Linux では通常該当しない（Windows ではよく起こる）

Windows では、ウイルス対策ソフトの検査対象外にするのは、データディレクトリ、WAL アーカイブの出力先、テーブルスペースのディレクトリ。必要なら `postgres.exe` も除外プロセスにする。

## 設定・ログの読み方

- `postgresql.conf` の項目をコメントアウトするとデフォルト値になる（空のファイルでも起動する）。デフォルトがコメント例の値と違うものがある: `client_encoding` は DB の文字エンコーディング、`bonjour_name` はコンピューター名、`wal_sync_method` は Linux では `fdatasync`。
- `wal_buffers` は 16MB（WAL セグメントサイズ）を超えて増やしても速くならない。書き込み中にセグメントが必ず切り替わり、そのたびに低速なディスクへの書き込みが入るため。
- `shared_preload_libraries` は起動時にライブラリを読み込み、クラスタ全体に効く。`CREATE EXTENSION` はそれを実行した DB の中にオブジェクトを作るだけで、効くのはその DB だけ。
- `pg_settings` で `context` が `internal` の項目は、DB 作成後に変更できない。
- Windows の `postgres.exe` は、Windows の一時領域（環境変数 `TEMP` / `TMP`）を使わない。
- `huge_pages = try` のままだと、Windows で「メモリ中のロックページ」権限が無い場合に起動時に `could not enable Lock Pages in Memory user right` が DEBUG で出る。対応は不要。出したくなければ `off`。
- `initdb` に渡したオプションは保存されない。`\l` で `template0` / `template1` の照合順序を見て推定する。`template1` の oid が 1 で `template0` の oid が他の DB より小さければ、作り直されていない。作り直されていれば、現在のテンプレートのロケールが新規 DB のデフォルトになる。
- ロケール指定なしの `initdb` では環境変数が効く。優先順位は `LANG` < `LC_*` < `LC_ALL`。確認は `localectl` よりも、より多くの変数を出す `locale` コマンド。
- `initdb` が「ロケール ja_JP.UTF-8 用の適切なテキスト検索設定が見つかりません。simple に設定しました」と出ても問題ない。`default_text_search_config` を `pg_catalog.english` にしてもよい（日本語向けの設定は元から無い）。

## ログメッセージの意味

- VACUUM の `WARNING: relation "..." page N is uninitialized`: テーブル拡張後、ページの初期化前にクラッシュした名残のゼロページを再利用したときのログ。データ破損ではない。
- `last completed transaction was at log time`: クラッシュリカバリ後のログ。コミット応答を返した変更が失われたわけではない。

## WAL に出力されないもの

UNLOGGED のテーブル・インデックス、一時テーブルとそのインデックス、外部テーブル、実行時統計情報、`ALTER SYSTEM` の設定変更、レプリケーションスロットの状態。拡張が提供するインデックスにも WAL を出さないものがある（スタンバイに複製されない）。シーケンスは採番のたびではなく、まとめて WAL に出る。プリペアドトランザクション（`PREPARE TRANSACTION`）は WAL に記録され、スタンバイにも複製される（[公式: PREPARE TRANSACTION](https://www.postgresql.org/docs/current/sql-prepare-transaction.html) は状態が「ディスクに完全に保存される」とし、[max_prepared_transactions](https://www.postgresql.org/docs/current/runtime-config-resource.html) はスタンバイ側にプライマリ以上の値を要求する）。

## その他

- `CLUSTER` を特定のテーブルに実行しても、他のテーブルへの操作は待たされない。ただし CPU とディスク I/O を使うので、サーバー全体の処理能力は落ちうる。処理が少ない時間帯に実行する。
- ストリーミングレプリケーションはプライマリとスタンバイのマイナーバージョンが違っても動く。メジャーが違うときは論理レプリケーションを使う。
- 論理レプリケーションは複製元と複製先のテーブル構造が同一でなくてよいので、入力用 DB にはインデックスを張らず、非同期で複製した分析用 DB にだけインデックスを張る、という使い分けができる。入力側の INSERT が速くなる代わりに、分析側のデータは少し遅れる。
- TOAST に回るぎりぎりのサイズの値が、読み出しは最も遅い。中途半端なサイズのテキストが多いなら、`toast_tuple_target` を下げて早めに TOAST させるか、テーブルを分割する。
- `COPY TO` の連続実行では、同じテーブルがキャッシュに残っていれば再利用される。大量のページを読む操作では、共有バッファを押し出し過ぎないよう直前に使った領域を使い回すことがある。Windows は `shared_buffers` を小さめにするので OS のキャッシュが支配的。
- 前段（bind）や COMMIT の遅延は、異常動作とは限らない。bind はパラメーター数が多い・計画作成に時間がかかる場合、COMMIT は更新を含む同時トランザクションが多くて WAL 同期書き込みの排他待ちが出る場合や、WAL 出力先ストレージの同期書き込みが遅い場合に起きる。サーバーの CPU・ディスク I/O・メモリの時系列を取って切り分ける。
- psqlODBC で 256 バイトを超える TEXT 値が欠ける場合は、`MaxVarcharSize`（接続文字列では `B0`、デフォルト 255）を疑う。`B0=8192;` を接続文字列に足して直るか確認する。`B3=1`（通信ログ）と `B2=1`（デバッグログ）でクライアント側に `C:\temp` や `/tmp` へログが出る。
- autovacuum は、処理中のテーブルに別セッションがロックを要求するとキャンセルされる（ログに cancel のメッセージが出る）。手動の VACUUM はキャンセルされない。古いトランザクションが残っていると、更新済みの行は回収されない。
- WAL セグメントが切り替わる契機は、16MB への到達、再起動、`pg_switch_wal()`、ベースバックアップの取得、`archive_timeout` の経過（[公式](https://www.postgresql.org/docs/current/runtime-config-wal.html)。前回の切り替えから設定時間が経ち、かつ何らかの更新があったとき）。それ以外の切り替わりは、その時間帯のログと `pg_waldump` で前後の WAL を見て調べる。
