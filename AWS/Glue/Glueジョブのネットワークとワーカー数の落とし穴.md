# Glue ジョブのネットワーク設計とワーカー数の落とし穴（VPC・サブネット・S3 エンドポイント・IP 枯渇）

（2021-11 時点のメモ）VPC 内の DB に接続する Glue ジョブを作るときに、接続定義まわりで踏みやすい点の整理。

## ジョブが動く場所は「接続」のサブネットで決まる

接続定義を作るとき、VPC とサブネットを割り当てる。ジョブが実行されるネットワークも、ジョブに設定した接続のサブネットで決まる。JDBC で DB に直接アクセスする場合は、その接続のサブネットから DB に届くか（ルーティング、セキュリティグループ）を確認する。

## S3 を参照しないジョブにも S3 の VPC エンドポイントが要る

ジョブのスクリプトや依存ライブラリは S3 から取得される。そのため、スクリプトが S3 のデータを一切読み書きしなくても、接続のサブネットがある VPC に S3 の VPC エンドポイント（Gateway 型）が必要になる。

エンドポイントが無いと、ジョブは開始前に S3 に届かず失敗する（NAT Gateway があれば別経路で通る）。

## ワーカー 1 台ごとにプライベート IP を 1 つ消費する

ジョブを実行すると、ワーカー数に応じてサブネットのプライベート IP が消費される（ワーカー 1 台が 1 つの ENI = 1 つの IP に対応する。[AWS ブログ](https://aws.amazon.com/blogs/big-data/scale-aws-glue-jobs-by-optimizing-ip-address-consumption-and-expanding-network-capacity-using-a-private-nat-gateway)）。小さいサブネット（例えば `/28`）を割り当てると、ワーカー数を増やしたときに IP が足りなくなる。ジョブ用のサブネットは余裕のある CIDR にする。

## ワーカーを増やしても速くならないことがある

並列処理で速くするには、入力を分割して並列に読めなければならない。JDBC なら、SQL 側で分割する（パーティション列やハッシュで分割して読む）。分割できない読み込みのままワーカーを増やしても、課金と IP の消費が増えるだけになる。

## 2 つの接続をまたぐ連携はできない

RDS から別の RDS へ移すように、異なるサブネット（異なる接続）にあるデータストア同士を 1 つのジョブでつなぐことはできない。1 つのジョブに設定できる接続は実質 1 つなので、一度 S3 に出力して、別のジョブで取り込む。

## 補足: ファイルをデータカタログのテーブルにする利点と欠点

- 利点: 元のファイル形式を意識せずに扱える。パーティションを使える。カラムの型や統計情報（レコード数など）を見られる。DB のテーブルのように管理できる
- 欠点: データを取り込むためのクローリングが要る。テーブルのスキーマはファイルの状態と非同期なので、スケジュール設定でクローラーを定期的に走らせる必要がある
