# AWS の監視で決めたアラートのしきい値・通知レベルと、CloudTrail 由来アラートを受けたときの初動

EC2 / ECS / Aurora / ALB を使う業務システムの運用設計で決めた、アラートのしきい値と 2 段階の通知レベル、CloudTrail のメトリクスフィルタ由来アラートの対応手順の要点。しきい値を一から決めるときの出発点に使う。

（2021-09 時点のメモ）

## 通知を 2 段階に分ける

アラートは EventBridge から SNS（AWS Chatbot）または Lambda 経由でチャットに流し、チャンネルを 2 つに分けた。

| 通知レベル | 意味 |
| --- | --- |
| 対処が必要 | サービスダウンかそれに相当し、担当者のアクションが要る |
| 通知 | 自動化や定期処理の結果。正常終了以外が来たら要観察 |

## しきい値（すべて 1 分間隔で評価）

| 対象 | 条件 | 統計 / 継続 | レベル |
| --- | --- | --- | --- |
| ALB / NLB | HealthyHostCount が 0 | 最大 / 2 分 | 対処が必要 |
| ALB | ターゲットの 5XX が 10 超 | 合計 / 3 分 | 対処が必要 |
| ALB | ALB 自身の 5XX が 1 超 | 合計 / 1 分 | 対処が必要 |
| EC2 | CPU・メモリ使用率 90% 以上 | 平均 / 60 分 | 通知 |
| EC2 | ディスク使用率 90% 以上 | 平均 / 10 分 | 通知 |
| EC2 | StatusCheckFailed_System が 1 以上 | 最大 / 2 分 | 通知（自動復旧を併設） |
| ECS | RunningTaskCount が 0 | 最大 / 2 分 | 対処が必要 |
| Aurora | 接続数が max_connections の 90% 以上 | 10 分 | 対処が必要 |
| Aurora | CPU 90% 以上、FreeableMemory 1,000MB 以下 | 平均 / 60 分 | 通知 |

- 死活系（正常ホスト 0、タスク 0、5XX）は短く切り、リソース使用率は 60 分続いたときだけ通知にして、一時的なスパイクで鳴らさない
- EC2 のメモリ・ディスクは CloudWatch 標準メトリクスに無いので CloudWatch エージェントで取る。本番は EC2 の標準 5 分間隔ではなく 1 分間隔にした
- StatusCheckFailed_System には EC2 の自動復旧アクションを付け、復旧が走ったことのアラートは「正常に動いていれば対応不要、他のメトリクスに異常が無いことだけ確認」とした
- Aurora の接続数アラートが出たら、パラメータグループの `max_connections` を上げ、同時にアラームのしきい値も合わせて直す

## CloudTrail のメトリクスフィルタ由来アラート

CloudTrail を CloudWatch Logs に流してメトリクスフィルタとアラームを作った。対象は、セキュリティグループ変更、EC2 の作成・起動・停止、IAM ポリシー変更、認可エラー、コンソールのログイン失敗、VPC / ゲートウェイ / NACL の変更、CloudTrail 自体の変更、S3 バケットポリシー変更、root ユーザー使用。どのアラートも受けた側の初動は同じ形にした。

1. CloudWatch Logs で該当イベントを開き、誰が（`userIdentity.arn`）、いつ（`eventTime`）、何をしたか（`requestParameters`）を特定する
2. 心当たりのある正当な変更なら対応不要
3. 心当たりが無いなら変更を元に戻し、認証情報の漏洩を疑ってパスワード変更・IAM ユーザーの停止を行う
4. ネットワーク系（SG / NACL / VPC / ゲートウェイ）が不正に開いた場合は、VPC Flow Logs でその経路からデータが出ていないかを確認する

種別ごとの追加の見方は次のとおり。

- EC2 の作成・起動: 大量起動してのマイニングが典型的な被害なので、不審なインスタンスが無いかを見る
- IAM ポリシー変更: 同じ主体が前後で行った操作を CloudTrail で洗い出し、影響先にバックドアやデータ持ち出しが無いかを調べる
- 認可エラー: 単発の操作ミスなら不要だが、不正アクセスされたロールで出やすいメッセージなので、誰が何をしたかは必ず押さえる
- コンソールのログイン失敗: 1 回きりは問題にしない。繰り返されているなら該当 IAM ユーザーを削除し、MFA を徹底する
- CloudTrail の停止・変更: 必ず元に戻し、認証情報の漏洩を疑う
- S3 バケットポリシー変更: 戻したうえで S3 アクセスログからデータ漏えいの有無を確認する

## そのほかの定常通知の扱い

- パッチ適用（Systems Manager メンテナンスウィンドウ）の失敗: 業務影響は小さいので優先度は低い
- AWS Backup のジョブが ABORTED / FAILED / EXPIRED: メッセージを見て再実行か設定変更
- ECR のイメージスキャン: Critical / High が 1 件以上ならベースイメージを更新するか、提供元に対応を依頼する
- AWS Health のイベント: connectivity issues なら自システムへの影響が高い。マルチ AZ なら ALB / NLB から障害 AZ を切り離す
